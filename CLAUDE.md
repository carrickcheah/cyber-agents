# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

TypeScript — run from `typescript/`:

```bash
bun install
bun run build                              # tsc; this IS the typecheck (no separate script)
bun test
bun test tests/register.test.ts            # single file
bun test -t "coverage sums to the total"   # single test by name
```

Python — run from `python/`. Requires 3.13+. Tests run against `src/` directly, not an
installed package, so `PYTHONPATH=src` is mandatory:

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
PYTHONPATH=src python3 -m unittest tests.test_register -v
PYTHONPATH=src python3 -m unittest tests.test_register.TestHelpers.test_find_control -v
```

There is no linter or formatter configured in either package. CI (`.github/workflows/ci.yml`)
runs exactly the build + test commands above.

## Architecture

### Two packages, one API

`python/` and `typescript/` are **parallel implementations of the same library**, published
under the same name to both registries (`uv add llmsafety`, `npm i llmsafety`). They are
not a core plus a binding — each is complete and standalone.

**Any change to one must be mirrored in the other, including its tests.** The two test suites
assert the same invariants and are kept line-for-line comparable. A change landed in only one
language is a bug, not a partial feature.

Both packages have **zero runtime dependencies** by design — Python uses stdlib `urllib`,
TypeScript uses global `fetch`. Keep it that way; the only devDependency is `typescript`.

### Naming divergence between the two is deliberate

Each side follows its own language convention. Do not "fix" these to match:

| Concept | TypeScript | Python |
|---|---|---|
| Domain id | `"review-routing"` | `"review_routing"` |
| Capture mode | `"not-instrumented"` (both — this one is a data value, not an identifier) | same |
| Lookup helpers | `controlsFor`, `findControl` | `controls_for`, `find_control` |
| Coverage fields | `byEvidence`, `notInstrumented` | `by_evidence`, `not_instrumented` |

### The five domains

`alignment`, `guardrails`, `fairness`, `review_routing`, `compliance` — following Anthropic's
Responsible AI, Safety & Risk model. Each is a module exposing `check() -> CheckResult`.

In 0.1.0 only **guardrails** has real detectors (PII leakage, prompt-leak,
injection-compliance). The other four are shape-defining stubs that return
`passed: null, score: null` with a findings line explaining what they need. `CheckResult`
allows null on both fields specifically so a stub is distinguishable from a pass — never make
a stub return `passed: true`.

`probe()` sends one request to a live endpoint and returns the body as text; `audit()` probes
once and runs every domain's `check` on that response.

### The register is the core of 0.1.0

`register.ts` / `register.py` hold `REFERENCE_CONTROLS` — 44 controls extracted from a
production multi-tenant AI contact centre and scrubbed of deployment specifics. This data must
stay identical across both languages.

Read `docs/documentations/control-register.md` before changing the schema — it is the normative
spec for the pattern, and each field's shape encodes a lesson from a real audit.
`docs/documentations/control-catalog.md` renders the same 44 controls as a document; it must be
regenerated by hand when the source changes. `docs/documentations/design-principles.md` holds
the 20 principles + 15 mechanism patterns the controls implement.
`docs/documentations/control-classes.md` is the proposed (unimplemented) 0.2 class API.

Rules the schema encodes, all enforced by the mirrored test suites:

- **The register lives in shipped `src/`, not in a docs folder.** A real audit falsified the
  claim "the inventory is kept in the repo" because the inventory was gitignored. Source
  placement makes the claim true by construction.
- **Live status is deliberately not a field.** Compute it per request from evidence — a
  hardcoded status is exactly the unverifiable claim a register exists to replace.
- **`capture: "not-instrumented"` requires a `gap`.** "Absent is never zero": an
  uninstrumented control must say so rather than render a reassuring zero.
- **Deployment-owned fields ship empty** — `source`, `failing`, `verifiedBy`/`verified_by`,
  `verifiedHow`/`verified_how` describe *your* system, not the control's design. A test asserts
  the reference catalog leaves them unset. Adopters fill them in downstream.
- **Every control carries both audiences** — `claim` is a falsifiable statement for an auditor,
  `plain` is ~7 jargon-free words for the operator. Neither may be empty.
- **`shortLabel` is not named `label` on purpose** — rendering pipelines overwrite a `label`
  key with the category label, silently clobbering the control-level one.
- **ID numbering gaps are intentional.** RR skips 06 and 08; CP skips 04. In the originating
  system, questioning such gaps uncovered shipped guardrails with no register entry. Never
  renumber to close them.
- **`asi` and `asiName` travel together** — an ASI id without a name fails the tests.
- Ids match `^[A-Z]{2}-\d{2}$` and are unique. `VC-*` (voice channel) controls are filed under
  the guardrails category, not their own.

### Three evidence classes

`attestation` (is it armed?) < `detective` (did it fire?) < `test` (is it still proven?). They
are not interchangeable — a control that has never fired is indistinguishable from one switched
off unless all three are held apart. The split mirrors SOC 2's test-of-design vs
test-of-operating-effectiveness.

`verifiedBy` grades how a control was proven: `mutation` (the control was deliberately broken
in the shipped file, the suite went red, then restored) is the strongest, then `prod-read`,
then `unproven` — stated rather than left to look equal.

## Releasing

`.github/workflows/publish.yml` fires on a published GitHub Release (or manual dispatch) and
ships both packages after re-running both test suites. PyPI uses Trusted Publishing (OIDC, no
token); npm uses the `NPM_TOKEN` secret plus build provenance. Version lives in three places
that must be bumped together: `python/pyproject.toml`, `typescript/package.json`, and the
`version`/`__version__` constants in the two entrypoints.

The publish workflow calls `npm publish` directly — npm is the registry client there and that
line is correct despite the repo otherwise using bun.
